# 项目知识与交付流程深度调整

2026-11-05。范围已确认：仅 We-Manage。运维工具、仓库接入、工单和自动开发不涉及；用户提供的总结混合了其他工作。本文是问题核对与改造验收依据，不代表所有规划已上线。

## 已证实的缺口

| 现状 | 代码依据 | 影响 |
|---|---|---|
| 资产整理复制已有线索并追加待补充模板 | internal/wemanage/assets.go，assetSeed | 草稿数量不代表项目知识深度 |
| 问题类别直接映射为待决策 | 同上，category 到 kind 的映射 | 没有识别是否已解决、是否需要管理者判断 |
| 每个来源条目生成一个资产 | wm_assets 的 source_item_id + kind 唯一键 | 同一项目跨日变化分散，不能形成持续更新的完整手册 |
| 项目报告主要依赖候选引用的日报快照 | project_report.go、custom_summary.go | 缺少代码、接口、运行约束和原始日志的联合核对 |
| 当前模块没有仓库接入和工单执行流程 | internal/wemanage 路由与代码检索 | 不能演示成完整自动开发产品 |

上一版已实现的权限隔离、版本留存、原始来源保留继续沿用。36 项历史草稿不删除，也不自动升级为已验证知识。

## 改造后的工作对象

以项目为入口。项目下有连续时间线、业务知识、系统知识、已知问题、历史决定、可复用方法和验收依据。卡片只是查看方式，知识必须能组合成一次任务所需的上下文。

每条事实至少关联来源、来源版本、日期、适用范围、核实状态和访问范围。明确区分模型建议、实际执行、测试通过、上线和业务验收；新结论不能悄悄覆盖旧决定。冲突保留两方来源，供人核对。

## 本次实施链路

项目线索 → 相关人员完整日报 → 分批证据提取 → 引文和日期校验 → 跨日知识合成 → 问题状态与 Skill 条件流程 → 人工核对。

新增项目知识视图与进展摘要分开保存。每次记录来源快照、模型过程、实际 Token 和规则指纹；输入未变时复用版本，不重复调用。旧版模板草稿和原始记录继续保留。

## 验收条件

- 用至少两天材料检查状态变化，已解决的问题不能继续放在当前待办。
- 关键结论能展开逐字引文；引文日期、编号与材料匹配。
- 大材料分批，不截断，缺乏项目相关事实时不编造。
- Skill 图包含具体步骤、条件与目标节点；无效分支、不可达节点和无法到达结束点的流程不通过校验。
- 来源隐私变化后，分析与历史结果受现有权限过滤。
- 已生成的同输入结果可复用；新增来源形成新版本并可比较变化。
- 明确日报仍是摘要；需要核实原始操作时沿现有日志核查入口继续查，不能声称已经读完全部原始日志。

## 知识与 Skill 的质量要求

项目手册按项目合成，不按来源条目堆叠。遇到变化时先比较新旧证据，再产生更新建议。已解决的问题从当前待办中退出，但保留历史。

Skill 必须有触发场景、输入、步骤、分支条件、验证、停止条件和来源。图与文字使用同一份结构化数据。只有一个案例时明确标为单案例方法；关键步骤无依据时保持草稿。不能只在章节之间画箭头就称为流程建模。

## 本轮交付边界

本轮验收针对真实项目的来源、证据、跨日知识、方法流程和待审核版本。运维工具的仓库、工单、自动开发、录屏及商业化方案不属于此次修改。未授予新人员管理权限，也未发布对外材料。
