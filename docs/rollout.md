# 分阶段上线与跨境数据库

本文回答两件事：服务放海外、数据库放国内怎么部署；怎么从一个人用起，逐步推到全公司。

## 一、拓扑：服务在海外，数据在国内

```
员工（国内）
   │ HTTPS
   ▼
海外服务器 ─────────────────────────────────────────────┐
│ Caddy → gateway → CPA → 每组固定出口代理 → chatgpt.com │
│            │  本地 spool（数据库断了先落这里）          │
└────────────┼───────────────────────────────────────────┘
             │ 跨境 · TLS · 仅白名单
             ▼
国内云 ──────────────────────────────┐
│ PostgreSQL（账本、用户、审计、风控） │
│ 对象存储 OSS / COS（对话原文，可选）  │
└──────────────────────────────────────┘
```

- **为什么服务必须在海外**：CPA 要连 chatgpt.com，并通过每个账号的代理出口。放在国内的话，这些代理连接要穿过防火墙，很容易被识别和阻断。
- **为什么数据库可以在国内**：请求路径上几乎不直接等数据库。Key 查询缓存 3 秒，设备状态缓存 15 秒，写日志和风控检测都在后台异步做。

### 配置方法

在 `deploy/.env` 里：

```bash
# 不启动本机自带的 postgres
COMPOSE_PROFILES=
# 指向国内数据库；sslmode 至少 require
DATABASE_URL=postgres://gateway:密码@你的RDS地址:5432/gateway?sslmode=require&connect_timeout=10

# 原文也放国内（可选）：阿里云 OSS / 腾讯云 COS 的 S3 兼容接口
BLOB_BACKEND=s3
S3_ENDPOINT=oss-cn-shanghai.aliyuncs.com      # COS 示例：cos.ap-shanghai.myqcloud.com
S3_REGION=按云厂商“S3 兼容”文档填写对应地域
S3_BUCKET=ai-seat-logs
S3_ACCESS_KEY=...                              # 建议建一个只能访问这个桶的子账号
S3_SECRET_KEY=...
```

网关启动时会检查桶能否访问，地域、密钥或桶名填错会直接报错退出。OSS 和 COS 的访问方式网关会自动处理。

然后照常 `./init.sh` 或 `docker compose up -d`。网关启动时会自动建表迁移。

### 国内数据库要做的准备

1. **只放行海外服务器的 IP**（RDS 白名单或安全组）。不要对 `0.0.0.0/0` 开放 5432。
2. **开启 SSL**，连接串用 `sslmode=require`。如果要校验证书，用 `verify-full` 并挂载 CA 证书。
3. **建库和账号**：新建数据库 `gateway`，并用高权限账号先执行一次 `CREATE EXTENSION IF NOT EXISTS pg_trgm;`（原文检索要用；很多云 RDS 的普通账号没有建扩展的权限）。
4. **选地域**：挑到美国线路好的地域（上海、杭州、深圳的 BGP 机房）。海外服务器也尽量选对国内线路好的（美西，最好是 CN2 GIA 线路）。
5. **上线前实测**：在海外服务器上跑几次 `psql "$DATABASE_URL" -c 'select 1'`，晚高峰（20:00–23:00）再测一次，看延迟和是否断连。

### 每个请求要读写几次数据库

跨境往返一次约 150–250 毫秒，所以网关尽量不按请求读写数据库，而是在内存里记住能记住的东西、再定时批量写：

| 事情 | 做法 | 数据库读写 |
|---|---|---|
| 查 Key（请求要等它） | 缓存 3 秒；过期后先用旧结果放行，后台刷新 | 请求基本不用等；每个活跃 Key 约每 3 秒后台读一次 |
| 查设备状态（请求要等它） | 缓存 5 分钟；状态一改立即失效 | 每台设备约 5 分钟一次 |
| 写日志 | 会话状态和“哪些内容已存过”记在内存里；攒 1 秒（或 200 条）一起提交 | **所有人的日志合起来约每秒 1 次**，外加每个新会话读 1 次 |
| 设备、网络的最近使用 | 内存里累加 | 每 30 秒 1 次；首次出现的网络立即写 |
| 客户端版本统计 | 内存里累加次数 | 每个版本每 10 分钟最多 1 次 |
| 额度快照 | — | 每个账号每分钟最多 1 次（触发限额时立即写） |

改之前，一个请求大约要 8 次数据库往返，其中 2 次要让请求等着；现在稳态下平均不到 1 次，请求本身基本不用等。

写日志的几个细节：

- 同一次提交在一个事务里完成，要么全写进去，要么都不写。
- 数据库连不上时，这一批先落到本地 spool 文件，恢复后自动补录。
- 数据库连得上、但拒收了某一条记录（数据有问题）时，会改成逐条提交：正常的照常写入，被拒的那条放进 `rejected.jsonl` 等人看，不会反复重试、拖累别人。
- 网关正常停机时，会先等进行中的请求结束、把日志写完或落盘，再退出。进程被强杀时，最多丢最后约 1 秒还没提交的日志。
- 对话内容的“最近使用时间”最多一天刷新一次，所以清理任务会给对话内容多留 2 天，不会误删还在用的内容。

### 跨境链路的影响

| 情况 | 影响 |
|---|---|
| 正常 | AI 请求基本不等数据库；门户页面每次操作会慢零点几秒。 |
| 链路短暂中断 | 最近用过的 Key 继续可用，最多 10 分钟；日志先写到海外服务器本地的 spool 文件，恢复后每 30 秒自动补录；设置保持最后一次读到的值；风控的设备登记失败时直接放行；设备、网络的使用计数留在内存里，下一轮再写。 |
| 中断超过 10 分钟 | 请求返回 503 `gateway_unavailable`（不会误报“Key 无效”）；门户打不开；定时任务失败，下一轮自动重试。 |
| 网关重启时数据库连不上 | 网关起不来，Docker 会自动重试，直到数据库连上。 |

中断期间，管理员新做的冻结、作废 Key 要等链路恢复（最多 10 分钟）才生效。

### 合规上要知道的

数据库和对话原文存在国内，更好满足留存和内部管控要求。但**请求内容本身仍然要发给 OpenAI（境外）**，这一次出境不会因为数据库在国内而消失，告知和制度里要照实写。

### 连接方向：国内这边不需要出境

所有跨境连接都由**海外网关主动发起**，连入国内的数据库和对象存储；飞书接口、日报模型、OpenAI 也都由海外网关调用。国内云服务器（例如阿里云）即使完全不能访问境外 IP，这套架构也照常工作，只要允许海外服务器的 IP 入站。

阿里云上的注意事项：

- **用 RDS for PostgreSQL**，不要在 ECS 上用 Docker 自建。Docker Hub 在国内基本拉不下镜像。
- `pg_trgm` 扩展要用 RDS 的**高权限账号**创建一次。
- 如果跨境上传原文不稳定，把 `S3_ENDPOINT` 换成 OSS 的**传输加速**地址 `oss-accelerate.aliyuncs.com`。
- 如果入站连数据库也不理想，可以把数据库换到**香港**地域。连接质量好很多，但数据就不在境内了，要结合合规需求决定。

### 配置建议

| | 冒烟、试点（≤5 人） | 部门（约 20 人） | 全员（约 100 人） |
|---|---|---|---|
| **海外服务器**（Caddy + 网关 + CPA） | 1 核 2G，30G 硬盘 | 2 核 4G，40G | 2 核 4G（宽裕些用 4 核 8G），60G |
| **国内 RDS PostgreSQL** | 1 核 2G 基础版，20G | 2 核 4G，50G | 2 核 4G 起，高可用版，150–200G，开存储自动扩容 |
| **国内对象存储** | 可不开 | 建议开 | 开 |

估算依据（每人每天约 300 次请求）：

- **海外服务器吃的主要是内存和线路，不太吃 CPU。** 网关和 CPA 都是 Go 程序，常驻各一两百 MB；在途请求会暂存请求体（Codex 每轮都会把上下文整个发过来，一般几百 KB）；日志队列上限 512 条，超出部分写本地磁盘。
- **硬盘要给数据库断线时的本地缓存留空间。** 断线期间日志带着完整请求体写到本地，100 人高峰期断一小时大约要几 GB。
- **数据库里最占地方的是原文检索表**（每个请求新增的对话文字加全文索引）。100 人大约每天 0.5–1GB，按 180 天保留约 100–160GB。请求明细表每年再加 10–20GB。原文放进对象存储后，数据库只存编号，容量主要就是这两项。
- **流量**：100 人时，员工上传到网关、网关再经代理发往 OpenAI，方向各约每天 6GB，每月约 200GB。静态代理如果按流量计费会比较贵，优先选按 IP 包月、不限流量的。回国内数据库的日志经过压缩和去重，每月只有几 GB。
- **线路比配置重要**：海外服务器优先选对国内线路好的（美西 CN2 GIA，或香港、日本机房）。

## 二、员工从国内访问：直连，不自建隧道

员工直接用 HTTPS 访问海外网关。这是普通的网站和接口流量（包括流式返回），不带代理协议的特征，防火墙也看不到加密内容，被针对性封锁的风险低。真正要关心的是**线路质量**：晚高峰的延迟和丢包。

- **网关服务器上不要装任何代理软件**（xray、3x-ui 之类），同一个 IP 既跑代理又跑网关会明显更显眼。
- **网关域名只在公司内部用**，不要外传。
- **选对国内线路好的海外机房**：美西 CN2 GIA 线路，或者香港、日本机房（再通过每组账号的美国代理出口，OpenAI 看到的仍是美国 IP）。
- **不要用国内服务器自建隧道转发**，原因：
  - 自建隧道反而是防火墙重点识别的流量；
  - 云厂商禁止用云服务器做跨境代理，会连累同一账号下的数据库；
  - 在国内服务器上对外提供网站，域名要 ICP 备案；
  - 自建的跨境通道有监管风险；
  - 所有请求的来源 IP 都会变成隧道服务器，防 Key 外泄的"不同网络同时使用"检测会失效。
- **实测**：试点阶段让员工分别在办公网、家里、手机热点上，于晚高峰执行：
  ```bash
  curl -o /dev/null -s -w 'connect %{time_connect}s  tls %{time_appconnect}s  total %{time_total}s\n' https://<网关域名>/healthz
  ```
  实在太差时，走运营商或云厂商的**合规跨境专线**，不要自建隧道。

## 三、分阶段上线

核心思路：**谁能登录，由飞书应用的「可用范围」决定；谁能真正用 AI，由管理员有没有给他绑定账号决定。** 这两个开关都可以一个人一个人地放。

| 阶段 | 范围 | 做什么 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 冒烟 | 只有你 | 先在「添加账号 → Kimi Code（试用）」接一个 Kimi 订阅，跑通飞书登录、领 Key、Codex 对话、日志、风控、团队用量；再换一个不怕丢的 ChatGPT 账号跑几天。风控用「宽松」。跑完 `docs/verification` 的 A 类和 B 类。 | 登录、发 Key、Codex 正常对话、日志能查、额度能显示、飞书消息能收到；跨境库晚高峰也稳定 |
| 1 试点 | 3–5 人，1–2 周 | 可用范围只加这几个人，逐个绑定账号；风控切到「标准」；每天看总览（降智、限额）和风险中心（误判）。 | 没有降智信号；没有无法解释的冻结；员工能自己完成新设备确认 |
| 2 部门 | 约 20 人 | 扩大可用范围；每 5–10 个账号一个出口 IP 组；原文切到对象存储；开始用 AI 日报。 | 一周内没有需要人工处理的账号异常 |
| 3 全员 | 全公司 | 可用范围设为全员；补齐每日备份和恢复演练（见 `operations.md`）。 | — |

**回退很简单**：ChatGPT 账号本来就属于公司，员工把 Codex 改回官方登录，或者管理员解绑账号，就不再经过网关。已记录的日志和审计都留在数据库里。
