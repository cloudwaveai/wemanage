# 分阶段上线与跨境数据库

本文回答两件事：服务放海外、数据库放国内怎么部署；怎么从一个人用起，逐步推到全公司。

## 一、拓扑：服务在海外，数据在国内

```
员工（国内）
   │ HTTPS
   ▼
海外服务器 ─────────────────────────────────────────────┐
│ Caddy → gateway → CPA → 每组固定出口代理 → chatgpt.com │
│            │  本地 spool（数据库断了先落这里）          │
└────────────┼───────────────────────────────────────────┘
             │ 跨境 · TLS · 仅白名单
             ▼
国内云 ──────────────────────────────┐
│ PostgreSQL（账本、用户、审计、风控） │
│ 对象存储 OSS / COS（对话原文，可选）  │
└──────────────────────────────────────┘
```

- **为什么服务必须在海外**：CPA 要连 chatgpt.com，并通过每个账号的代理出口。放在国内的话，这些代理连接要穿过防火墙，很容易被识别和阻断。
- **为什么数据库可以在国内**：请求路径上几乎不直接等数据库。Key 查询缓存 3 秒，设备状态缓存 15 秒，写日志和风控检测都在后台异步做。

### 配置方法

在 `deploy/.env` 里：

```bash
# 不启动本机自带的 postgres
COMPOSE_PROFILES=
# 指向国内数据库；sslmode 至少 require
DATABASE_URL=postgres://gateway:密码@你的RDS地址:5432/gateway?sslmode=require&connect_timeout=10

# 原文也放国内（可选）：阿里云 OSS / 腾讯云 COS 的 S3 兼容接口
BLOB_BACKEND=s3
S3_ENDPOINT=oss-cn-shanghai.aliyuncs.com      # COS 示例：cos.ap-shanghai.myqcloud.com
S3_REGION=按云厂商“S3 兼容”文档填写对应地域
S3_BUCKET=ai-seat-logs
S3_ACCESS_KEY=...                              # 建议建一个只能访问这个桶的子账号
S3_SECRET_KEY=...
```

网关启动时会检查桶能否访问，地域、密钥或桶名填错会直接报错退出。OSS 和 COS 的访问方式网关会自动处理。

然后照常 `./init.sh` 或 `docker compose up -d`。网关启动时会自动建表迁移。

### 国内数据库要做的准备

1. **只放行海外服务器的 IP**（RDS 白名单或安全组）。不要对 `0.0.0.0/0` 开放 5432。
2. **开启 SSL**，连接串用 `sslmode=require`。如果要校验证书，用 `verify-full` 并挂载 CA 证书。
3. **建库和账号**：新建数据库 `gateway`，并用高权限账号先执行一次 `CREATE EXTENSION IF NOT EXISTS pg_trgm;`（原文检索要用；很多云 RDS 的普通账号没有建扩展的权限）。
4. **选地域**：挑到美国线路好的地域（上海、杭州、深圳的 BGP 机房）。海外服务器也尽量选对国内线路好的（美西，最好是 CN2 GIA 线路）。
5. **上线前实测**：在海外服务器上跑几次 `psql "$DATABASE_URL" -c 'select 1'`，晚高峰（20:00–23:00）再测一次，看延迟和是否断连。

### 跨境链路的影响

| 情况 | 影响 |
|---|---|
| 正常 | 每次跨境往返约 150–250 毫秒。AI 请求只在缓存过期时多等一次（每个 Key 大约每 3 秒一次），相比模型回复的几秒到几十秒可以忽略。门户页面每次操作会慢零点几秒。 |
| 链路短暂中断 | 最近用过的 Key 继续可用，最多 10 分钟；日志先写到海外服务器本地的 spool 文件，恢复后每 30 秒自动补录；设置保持最后一次读到的值；风控的设备登记失败时直接放行。 |
| 中断超过 10 分钟 | 请求返回 503 `gateway_unavailable`（不会误报“Key 无效”）；门户打不开；定时任务失败，下一轮自动重试。 |
| 网关重启时数据库连不上 | 网关起不来，Docker 会自动重试，直到数据库连上。 |

中断期间，管理员新做的冻结、作废 Key 要等链路恢复（最多 10 分钟）才生效。

### 合规上要知道的

数据库和对话原文存在国内，更好满足留存和内部管控要求。但**请求内容本身仍然要发给 OpenAI（境外）**，这一次出境不会因为数据库在国内而消失，告知和制度里要照实写。

## 二、分阶段上线

核心思路：**谁能登录，由飞书应用的「可用范围」决定；谁能真正用 AI，由管理员有没有给他绑定账号决定。** 这两个开关都可以一个人一个人地放。

| 阶段 | 范围 | 做什么 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 冒烟 | 只有你 | 海外一台服务器 + 国内数据库；飞书登录；1 个不怕丢的 ChatGPT 账号；风控用「宽松」。跑完 `docs/verification` 的 A 类和 B1–B11。 | 登录、发 Key、Codex 正常对话、日志能查、额度能显示、飞书消息能收到；跨境库晚高峰也稳定 |
| 1 试点 | 3–5 人，1–2 周 | 可用范围只加这几个人，逐个绑定账号；风控切到「标准」；每天看总览（降智、限额）和风险中心（误判）。 | 没有降智信号；没有无法解释的冻结；员工能自己完成新设备确认 |
| 2 部门 | 约 20 人 | 扩大可用范围；每 5–10 个账号一个出口 IP 组；原文切到对象存储；开始用 AI 日报。 | 一周内没有需要人工处理的账号异常 |
| 3 全员 | 全公司 | 可用范围设为全员；补齐每日备份和恢复演练（见 `operations.md`）。 | — |

**回退很简单**：ChatGPT 账号本来就属于公司，员工把 Codex 改回官方登录，或者管理员解绑账号，就不再经过网关。已记录的日志和审计都留在数据库里。
